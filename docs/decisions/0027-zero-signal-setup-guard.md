# ADR-0027: Zero-signal setup guard — warn loudly always, gate the write only on zero catalog matches

- **Status:** Proposed | **Date:** 2026-08-05
- **Decided by:** Aniisa Bihi (draft by Claude)
- **Affects:** `src/commands/scan.ts`, `src/claude/setup-core.ts`, `src/commands/setup-project.ts`, `src/cli.ts`, `src/recommender/policies.ts`, `src/recommender/recommend.ts`, `src/scanner/detection.ts`
- **Related:** [docs/plans/workspace-detection-and-permissions-fixes.md](../plans/workspace-detection-and-permissions-fixes.md) (Task 1.2 / D1), [docs/plans/workspace-worktree-materialization.md](../plans/workspace-worktree-materialization.md) (Task 1 — `resolveRoots()`, the worktree signal this guard consumes)

## Context

`haus scan` computed `detectionStatus: 'unknown'` (no recognised role or stack signal) but printed nothing about it — a user reading "Roles: unknown" on stdout had no explanation and no pointer to what to do next. The only place the condition surfaced in prose was `setup-project`'s recommender warnings (`mergeRecommendationWarnings` in `src/recommender/policies.ts`), and even there the message didn't distinguish a genuinely stack-less project from a `git worktree` checkout where sibling repos referenced by the workspace simply aren't materialized on disk at that path — a scenario that reads identically to "no stack" but has a different fix (run from the main checkout, or the workspace root, not the worktree).

Separately, `setup-project` always wrote `recommendation.json` (and, once applied, `haus.lock.json`) regardless of whether anything in the catalog actually matched the project. On a truly zero-signal repo this means running `setup-project` silently produces an artifact set representing "nothing recommended" with no acknowledgement that this might be a detection gap rather than an accurate result.

This depends on two things already landed on this branch: `resolveRoots()`/`isLinkedWorktree` (`src/utils/git-root.ts`, worktree-safe root resolution) and the D9 nested-repo scanner boundary fix (`src/utils/fs.ts`) — without the latter, a leaked sibling repo's stack could falsely satisfy "non-zero signal" and this guard would never trigger when it should.

## Decision

1. **Warn loudly by default, unconditionally, in both surfaces.** `haus scan` now prints a `WARN:` line whenever `detectionStatus === 'unknown'` (previously silent). `setup-project`'s recommendation warnings do the same via the existing `mergeRecommendationWarnings` path. Both share one message builder — `describeUnknownDetection()` in `src/scanner/detection.ts` — so the wording can't drift between the two commands.
2. **The message names the linked-worktree condition explicitly when it applies.** `describeUnknownDetection()` takes `isLinkedWorktree` (from `resolveRoots()`) and appends a clause naming the worktree case specifically — distinguishing "no stack detected" from "no stack detected, and you're running from inside a git worktree, so sibling repos may not be on disk here" — rather than leaving the user to guess why a repo they know has a stack reads as zero-signal.
3. **The write is gated behind `--force`, but only on a true zero-catalog-item match — not zero detected stacks.** `runSetupCore` (`src/claude/setup-core.ts`) now refuses to write `recommendation.json`/`haus.lock.json` when `recommendation.recommended.length === 0` and `--force` was not passed, printing a message that tells the user to re-run with `haus setup-project --force`. Passing `--force` (new `SetupCoreOptions.force`, wired through `setup-project.ts` and the `--force` CLI flag) writes as before. Crucially, the gate checks _catalog matches_, not _detected stacks_: a project with zero recognised stacks but at least one stack-agnostic catalog match (e.g. a default-baseline reviewer agent, or any tag-only item) still has `recommended.length >= 1` and writes normally with no `--force` needed.

## Motivation (why)

- A silent `detectionStatus: 'unknown'` is a UX trap: the user has no signal that haus didn't recognise their stack, so they can't tell whether "Roles: unknown" means "nothing to detect" or "haus is missing support for this ecosystem" — the fix differs in each case (nothing to do vs. file an issue / add a marker).
- The worktree case is a distinct failure mode from genuine zero-signal, discovered via the original bug report: running haus from inside a Claude-Code-created (or any `git worktree add`ed) checkout can make an otherwise-normal project look stack-less if the scan or workspace logic expects sibling repos materialized at paths that only exist in the main checkout. Silently treating that the same as "this repo really has no stack" sends the user down the wrong troubleshooting path.
- Gating the artifact write (rather than only warning) matters because `recommendation.json`/`haus.lock.json` are inputs to `haus apply`/`haus doctor` — a project that produced literally zero catalog matches and then gets `apply`'d anyway installs a `.claude/` directory of just core files with no acknowledgement that detection may have failed, and no clear "did I mean to run this here" moment. `--force` supplies that moment without permanently blocking legitimate zero-match cases from proceeding once acknowledged.
- Scoping the gate to zero _catalog matches_ rather than zero _detected stacks_ is the load-bearing distinction: nearly every real project matches at least the default-baseline catalog items (stack-agnostic workflow/security guidance), so a "zero detected stacks" gate would fire on almost every unrecognised-stack project and turn a common, already-supported path (stack-agnostic-only guidance) into a forced `--force` prompt — regressing the exact audience (unsupported-ecosystem users still getting baseline guidance) the `detectionStatus: 'partial'`/`'unknown'` handling was built to serve in the first place.

## Alternatives considered

- **Hard-block the write always on `detectionStatus === 'unknown'`, no `--force` escape hatch.** Rejected — this conflates "no recognised stack" with "no useful catalog match," which are different conditions (see above); it would force every unsupported-ecosystem or worktree-affected user through a manual override just to get the baseline stack-agnostic skills they're already entitled to, with no correctness benefit.
- **Warn-only forever, never gate the write.** Rejected as insufficient on its own — a warning that scrolls past in a large setup transcript is exactly the failure mode the original bug report describes (80 skills written from a leaked sibling stack, discovered only much later). A true zero-catalog-match run is rare enough, and consequential enough (it usually means something upstream is misconfigured — wrong cwd, empty/misdirected catalog fixture, or a stale cache), that requiring one explicit acknowledgement is proportionate; it is not the common case a bare warn-only design would need to tolerate silently forever.
- **Gate on zero detected stacks (`detectionStatus === 'unknown'`) instead of zero catalog matches.** Considered and rejected per the Motivation section — this is the regression this ADR is explicitly designed to avoid; it was the original (pre-fix) design sketch in the plan and was revised specifically because it would break the common stack-agnostic-only case.

## Consequences

- `setup-project` (and any caller of `runSetupCore`, including the workspace setup loop, which does not currently pass `force` and so inherits the same default-refuse behavior per-repo) now exits non-zero and skips the recommendation/lock write on a true zero-catalog-match run unless `--force` is passed. This is a behavior change from "always writes, possibly with a warning" to "refuses by default" for that one specific condition — deliberate, but worth knowing if a downstream script or CI job depends on `setup-project` always producing a `recommendation.json` unconditionally.
- `mergeRecommendationWarnings()` gained a second, optional `isLinkedWorktree` parameter (default `false`) to stay backward-compatible with existing direct callers/tests that construct a `ContextMap` without resolving worktree state.
- The worktree-awareness clause only fires when `resolveRoots()` reports `isLinkedWorktree: true` — a non-git directory or a bare repo (both `isGitRepo: false`) never triggers it, matching `resolveRoots()`'s existing fail-safe fallback semantics.
