# ADR-0025: Untrack machine-local scan artifacts — gitignore-writer, apply-time migration, absolute-path removal

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decided by:** Aniisa Bihi (draft by Claude)
- **Affects:** `src/claude/write-gitignore.ts` (new), `src/commands/apply.ts`, `src/commands/doctor.ts`, `src/types.ts`, `src/scanner/scan-project.ts`, `src/claude/write-workflow-config.ts`, `tests/write-gitignore.test.js`, `tests/apply-gitignore-untrack.test.js`, `tests/doctor-gitignore.test.js`, `tests/scan-project-no-absolute-path.test.js`
- **Related:** [docs/plans/workspace-worktree-materialization.md](../plans/workspace-worktree-materialization.md) (Task 2), [ADR-0006](0006-ownership-marking-on-frontmatter-files.md) (the managed-block sentinel convention reused here), `src/claude/write-prettierignore.ts` (the existing `.prettierignore` managed block this mirrors)

## Context

An already-landed data-corruption incident in `vafab-workspace` (a real multi-repo consumer of haus) surfaced that `context-map.json`, `recommendation.json`, and `sources-report.json` — all written by `haus scan`/`haus apply` on every run — were tracked in the consumer repo's `main` branch. `context-map.json` there carried an absolute path to a since-deleted worktree (`/Users/tim/Development/vafab-workspace/.claude/worktrees/haus-workflow-update-5c3bac`), and its `repoRoles`/`detectedStacks` were stale relative to the real repo. `haus doctor` in that repo then reported the dead worktree's slug as the repo name, not the real one.

Re-verification against this codebase's `src/` (not taken on the incident report's word) confirmed:

- haus has **zero** `.gitignore`-writing code anywhere today — this is new capability, not an extension of an existing template.
- `context-map.json`, `recommendation.json`, and `sources-report.json` are all written under `.haus-workflow/` via `hausPath()` (`src/scanner/scan-project.ts`, `src/scanner/write-sources-report.ts`, `src/claude/setup-core.ts`) and are pure scan/recommendation output — machine-local, regenerated on every run, and never meant to be a source of truth in git.
- `context-map.json`'s `root` field (`src/types.ts`) was an absolute path, serialized verbatim on every scan (`src/scanner/scan-project.ts`), confirmed by grep to have **no reader anywhere in `src/`** — nothing ever consumed it back off a scanned `ContextMap`.
- `deep-context.json` (also under `.haus-workflow/`, read by `src/recommender/recommend.ts`) is written by the **writing-documentation skill** — LLM-authored at runtime in the `haus-workflow-catalog` repo, not by this CLI's code. Gitignoring its path is CLI-side (gitignore doesn't care who writes a file into it); making the skill itself stop embedding absolute paths is a separate, catalog-side track.
- `haus.lock.json` is a different case entirely: it's a registry of catalog content haus installed into the repo's own tracked content (skills, agents, commands, templates) and correctly stays tracked at the repo root. It is explicitly **not** in scope here.
- `setup-answers.json`, named in the originating ticket as a sixth artifact needing the same treatment, has **zero references anywhere in this CLI's current `src/`/`library/`** — no reader, no writer. Building migration/untracking logic for a file this codebase has no relationship to risks either dead code or guessing wrong about a schema that may belong to a haus version predating this one.

## Decision

1. **New module, `src/claude/write-gitignore.ts`**, ensures a project's `.gitignore` covers four repo-relative artifact paths: `.haus-workflow/context-map.json`, `.haus-workflow/recommendation.json`, `.haus-workflow/sources-report.json`, `.haus-workflow/deep-context.json`. It is additive and idempotent: it never clobbers a user's existing `.gitignore` entries, and it skips an artifact path already covered — verbatim or by an already-present broader directory pattern (e.g. a plain `.haus-workflow/` entry) — via simple exact-line/directory-prefix detection, deliberately not a full gitignore pattern-matching engine.
2. **Sentinel convention reused, not reinvented.** The managed block uses the same `# HAUS:BEGIN haus-managed v=1` / `# HAUS:END haus-managed` comment-pair sentinel `write-prettierignore.ts` already established for `.prettierignore` (ADR-0006 style), rather than the markdown `<!-- HAUS-MANAGED ... -->` header `write-workflow.ts` uses for content-hash tamper detection. `.gitignore` syntax has no comment-block convention of its own to extend, and unlike `WORKFLOW.md`, there is no template content whose tamper-vs-stale-vs-legacy state needs distinguishing — a plain sentinel pair marking "haus owns the lines between here" is the right-sized mechanism, matching `.prettierignore`'s own precedent for exactly this reason.
3. **`haus apply --write` migrates existing projects.** After writing `.claude/` content, it calls the gitignore-writer, then checks (`git ls-files`) whether any of the four artifact paths are currently tracked. Each one found is `git rm --cached`'d (never `rm -f`'d — the working-tree file is left in place) with an explicit, non-silent explanation printed per file: what happened, why, and to run `git status` before committing the change. This is idempotent — a second run finds nothing tracked and prints nothing.
4. **`haus doctor` flags any artifact still tracked**, printing the exact `git rm --cached <path>` fix command (or the one-line `haus apply --write` alternative that does the same automatically). This is a blocking finding (like the hooks-contract and CLAUDE.md-import-block checks), not an advisory suggestion — a machine-local, per-developer file leaking into the shared history is a real defect in the project's setup, not a matter of taste.
5. **`ContextMap` (`src/types.ts`) no longer has a `root` field at all**, rather than relativizing it. Grep confirmed zero readers of `context.root`/`ctx.root` anywhere in `src/` before removing it — this was the smaller, safer diff than introducing a repo-relative value nothing consumes, and it removes the absolute-path risk at the source rather than merely disguising it. `repoName` already carries the only root-derived signal downstream code (doctor, workflow-config) actually uses. This is defense-in-depth on top of (1)-(4): even if a `context-map.json` leaks into git again through some future misconfiguration, it structurally cannot carry a `/Users/<name>/...` or `/home/<name>/...` path, because the type has nowhere to put one.
6. **`setup-answers.json` is explicitly excluded from this work**, per the Context section above. It is not added to the gitignore-writer's pattern list, `haus apply` does not check it, and `haus doctor` does not flag it. If it turns out to be a real artifact from an earlier haus version, it needs its own investigation (confirmed against an affected workspace or its filer) before any code is written for it — not a guess folded into this change.

## Motivation (why)

- The vafab-workspace incident is not hypothetical or theoretical — it already happened, corrupted `main`, and produced a visibly wrong `haus doctor` report (dead worktree slug, empty roles) for every developer in that repo until manually fixed. The fix needs to (a) stop it from recurring in every haus-managed project going forward, and (b) actively repair projects it already happened to, not just document the correct behavior for new ones.
- `git rm --cached` (never deleting the working-tree file) was chosen deliberately: the migration must never destroy a file the user might still want on disk, only stop git from tracking it. This mirrors the caution already established in this codebase's other destructive-adjacent flows (ADR-0017's backup-before-prune, ADR-0019's restore safety model) — a data-safety default, not a new pattern.
- Making the untrack step non-silent (one explanatory line per file, not a silent background fix) matters because this changes what the user's next `git status`/`git commit` will show — an unannounced index change right before a commit is exactly the kind of surprise that erodes trust in a tool that's supposed to be safe to run repeatedly.

## Alternatives considered

- **Relativize `context-map.json`'s `root` field instead of dropping it** — rejected. The plan explicitly allowed either; grep confirmed nothing reads the field back, so a relative value would be dead weight with no consumer, carrying forward the same category of risk (a path field that could regress to absolute again) for zero benefit. Dropping it is strictly smaller and structurally safer.
- **Treat the doctor check as an advisory suggestion, not a blocking flag** — rejected. `doctor`'s own documented split is "flag = setup is broken/incomplete" vs. "suggest = works but could be improved." A tracked machine-local artifact is not a matter of polish — it's actively wrong content in the repo's shared history, the same severity class as a missing hooks contract or a broken CLAUDE.md import block, both of which are already blocking flags.
- **Fold `setup-answers.json` into the gitignore-writer's pattern list "just in case"** — rejected per the Context section: no writer for it exists anywhere in this codebase's current `src`/`library`, so adding untrack logic for it would either be dead code or an unverified guess about a file this CLI version has no relationship to. Explicitly deferred pending direct confirmation.
- **Fix `deep-context.json`'s absolute-path content here too** — rejected as out of scope for this ADR. The file is authored by the writing-documentation skill at runtime in the `haus-workflow-catalog` repo, not by this CLI; gitignoring its path is a CLI-side, zero-risk addition, but changing what the skill writes into it requires a catalog-repo change, tracked separately so it isn't silently dropped.

## Consequences

- **Every existing haus-managed project that had these artifacts tracked gets its git history "corrected going forward" on its next `haus apply --write`** — the files are untracked from that commit onward, but the incident's original absolute path (if any) still exists in that repo's git _history_ prior to the untrack commit. This ADR does not rewrite history (per `.haus-workflow/WORKFLOW.md`'s NEVER rule against it) — a repo that wants the old commits scrubbed needs a separate, explicit history-rewrite decision of its own, out of scope here.
- **`haus doctor` will report a new blocking finding** for any project that has one of these four artifacts tracked, immediately upon upgrading to a haus version with this change — before that project has run `apply --write` to fix it. This is intentional (it's what motivates the fix), but it means `doctor`'s exit code can flip from 0 to 1 purely from a haus version bump, with no other change to the project. Teams gating CI on `haus doctor`'s exit code should run `haus apply --write` as part of adopting the new haus version, not treat the new failure as a regression in their own repo.
- **`context-map.json`'s schema changes** (the `root` field disappears). Nothing in this codebase read it, but any external tooling a consumer team may have built against the old `context-map.json` shape that happened to depend on `root` will need to adjust. No migration is provided for external consumers of this file's schema — it was never a documented public contract.
- **`setup-answers.json` remains unaddressed.** If it does turn out to be a real, still-relevant artifact somewhere, a future ADR superseding this one is the correct vehicle once it's been confirmed rather than assumed.
