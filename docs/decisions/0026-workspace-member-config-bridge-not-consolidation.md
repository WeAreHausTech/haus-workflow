# ADR-0026: Workspace member config — bridge `repos.manifest.json` into the CLI, don't consolidate the three files yet

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decided by:** Aniisa Bihi (draft by Claude)
- **Affects:** `src/workspace/members.ts` (new), `tests/workspace-members.test.js` (new)
- **Related:** [docs/plans/workspace-worktree-materialization.md](../plans/workspace-worktree-materialization.md) (Task 3), [ADR-0025](0025-untrack-machine-local-scan-artifacts.md) (sibling Task 2 of the same plan), `src/commands/workspace/config.ts` (the pre-existing `haus.workspace.yaml` parser this bridges from), `docusaurus-docs/workspace.mdx` (documents the three-file split this ADR does not remove)

## Context

A multi-repo "workspace" in haus is described across three different files today, each read by a different consumer:

- `haus.workspace.yaml` — the only one of the three actually parsed by CLI code (`src/commands/workspace/config.ts`), driving `haus workspace discover/scan/setup/doctor`.
- `repos.manifest.json` — lists member repos (`id`, `folder`, `repo` URL) for the `project:clone` Claude Code skill. Read only by that skill's prose instructions; no CLI code has ever parsed it.
- `repos.local.json` — a `pathOverrides` map (`folder` -> absolute path) marking repos the user already has cloned elsewhere. Also skill-prose-only.

This is a confirmed, re-verified fact from the analysis behind the parent plan (`workspace-worktree-materialization.md`'s verdict table): "three-file config trap ... `haus.workspace.yaml` code-read; `repos.manifest.json`/`repos.local.json`/`localdev.yml` skill-doc vocabulary only." Task 4 of that plan (`haus workspace worktree add`) needs to enumerate a workspace's member repos from CLI code — and a real workspace may have configured its members via either file, since they were built independently for different jobs (cross-repo CLI ops vs. clone-time bootstrapping) and nothing before this ADR required them to agree.

## Decision

1. **Bridge now: teach the CLI to read both.** New module `src/workspace/members.ts` exports `readMembers(rootInfo): Promise<Member[]>`, normalizing either config source into one `Member` shape (`id`, `folder`, `url?`, `absPath`, `source`). `haus.workspace.yaml` is read via the existing `parseWorkspaceConfig`/`WORKSPACE_FILE` from `src/commands/workspace/config.ts` (no new YAML-parsing logic); `repos.manifest.json` gets new, minimal, tolerant parsing of its `{ repos: [{ id, folder, repo? }] }` shape.
2. **Precedence, not merge.** When both files are present, `haus.workspace.yaml` wins outright and `repos.manifest.json` is not consulted. It is already the config every `haus workspace <subcommand>` treats as authoritative; `repos.manifest.json` remains a clone-time ingredient list. No attempt is made to reconcile or merge overlapping entries between the two.
3. **`repos.local.json`'s `pathOverrides` is honored on top of whichever source wins**, matching the `project:clone` skill's existing behavior — a member's `absPath` reflects the override instead of the default `workspaceRoot/folder` join. Only the `pathOverrides` field is parsed (tolerantly); no full schema is built for the rest of that file, since nothing else in it is needed here.
4. **No migration for existing workspaces.** A workspace with only `haus.workspace.yaml` keeps working exactly as it does today (today's only real-world case). A workspace with only `repos.manifest.json` gains new CLI-side readability it didn't have before. Nobody is asked to move data between files, rename anything, or run a one-time conversion.
5. **The three-file trap remains a documented known wart**, not fixed here. `localdev.yml` is untouched by this change and stays skill-prose-only. Consolidating to a single config file is deferred to its own future ADR (see Alternatives below) — this ADR is scoped to making the CLI able to _read_ the second file, not to changing which file a workspace _should_ use going forward.
6. **Tolerant on read, strict on write.** `readMembers()` never writes anything. A config file that is present but fails to parse (malformed JSON/YAML) or has the wrong shape (e.g. `repos` not an array, an entry missing `id`/`folder`) throws a typed `MemberConfigError` rather than returning an empty array — so a broken config can never be silently mistaken by downstream logic (including Task 4's `worktree add`) for "this workspace legitimately has no members." An empty array is returned only when neither `haus.workspace.yaml` nor `repos.manifest.json` exists at all.

## Motivation (why)

- Task 4 (`haus workspace worktree add/remove/doctor`) needs one normalized way to enumerate member repos regardless of which file a given workspace happens to use — building that against only `haus.workspace.yaml` would silently fail for any workspace whose members are described purely by `repos.manifest.json` (plausible today, since that file predates any CLI code reading `haus.workspace.yaml` for the same purpose in some projects).
- A full consolidation (one file, one schema, replacing all three) is a bigger, riskier change: it needs a migration path for existing workspaces, a decision about which fields each of the three files' distinct concerns (cross-repo CLI config vs. clone bootstrapping vs. local-dev orchestration) collapse into, and coordination with the `project:clone`/`project:cloneandsetup` skill prose in the catalog repo. None of that has any urgency attached to it today — the bridge alone unblocks Task 4.
- Silently returning an empty list on a parse failure would be actively dangerous once Task 4 exists: `worktree add` finding "zero members" because a config file is malformed (rather than because the workspace has none) would either no-op with no members materialized, or — worse — read as "nothing to do" and report success. A thrown, typed error makes that failure mode impossible to miss.

## Alternatives considered

- **Consolidate to a single config file now** (e.g. extend `haus.workspace.yaml` with `folder`/`repo` fields and retire `repos.manifest.json`/`repos.local.json`) — rejected for this task. It is a bigger change requiring a migration path for every existing workspace, a redesign that has to account for `repos.local.json`'s different lifecycle (gitignored, per-developer, never committed, unlike `haus.workspace.yaml`), and touches the `project:clone` skill's contract in the separate catalog repo. Nothing about Task 3 or Task 4 requires it — deferred to its own future ADR when there is an actual driver for it.
- **Merge entries from both files when both are present** (union by `id`/`folder`, conflict-detect overlaps) — rejected as unnecessary complexity for a bridge. The two files have historically served different jobs and were never designed to describe the same member list; a workspace that has both today almost certainly has `haus.workspace.yaml` as the CLI-relevant one. A precedence rule is simpler, has an obvious explanation, and can be revisited if a real workspace surfaces a case where both are genuinely needed together.
- **Return `undefined`/empty on a broken config, matching `parseWorkspaceConfig`'s own existing tolerant-on-malformed-YAML behavior** — rejected. `parseWorkspaceConfig` returning `undefined` on malformed YAML is safe today only because every caller (`discover.ts`'s `runDiscover`) explicitly checks for that case and refuses to proceed, printing an error. `readMembers()` sits underneath a broader set of future callers (Task 4) that must never conflate "no config" with "broken config" — an explicit typed exception is the safer contract for a shared read layer with call sites this codebase doesn't fully know about yet.

## Consequences

- Any workspace using only `repos.manifest.json` becomes usable by CLI code (Task 4 and beyond) for the first time — a net-new capability, not a behavior change for existing `haus.workspace.yaml`-only workspaces.
- A workspace that happens to have both files will have its `repos.manifest.json` entries silently ignored by `readMembers()` — this is intentional precedence, not a bug, but it means a workspace author who edits `repos.manifest.json` expecting `haus workspace worktree` (Task 4) to pick it up will see no effect until they also update (or remove) `haus.workspace.yaml`. Worth a one-line callout in `docusaurus-docs/workspace.mdx` when Task 4/6 documents the worktree flow.
- `MemberConfigError` becomes a new failure mode any future caller of `readMembers()` must handle explicitly (catch-and-report, not ignore) — consistent with, not a departure from, this codebase's existing posture of surfacing broken config loudly (`MalformedJsonFileError` in `src/utils/fs.ts`, `runDiscover`'s refusal on a malformed existing yaml).
- The three-file trap is still real and still confusing to a new contributor reading `docusaurus-docs/workspace.mdx`'s existing three-row table — this ADR does not reduce that confusion, only stops it from also being a CLI capability gap. A future consolidation ADR remains open work, not committed to any timeline here.
